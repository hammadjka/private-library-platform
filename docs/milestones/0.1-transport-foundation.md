# Milestone 0.1 — Transport Foundation

**Status:** In progress

## Goal

Replace the development-only HTTP implementation with a mature, bounded, and
observable transport while preserving full-file playback, `HEAD`, byte-range
seeking, and the embedded browser client.

The work is deliberately divided into short, review-sized tasks. Each task
should end with:

1. a plain-language explanation of what changed and why;
2. the decision made and alternatives considered;
3. relevant Rust or networking concepts;
4. tradeoffs, limitations, and gotchas;
5. exact verification results; and
6. a two-to-four-question quiz before beginning the next task.

Quiz questions must only cover material explained during the task.

## Tasks

### 0.1.1 — Make the test server reliable

**Estimated focused time:** 30–60 minutes

**Status:** Complete (October 25, 2026)

The current tests reserve a port, release it, and then start the daemon on that
port. Another process can claim the port in between. Change the harness to let
the operating system assign the daemon's port and reliably discover the actual
address.

**Learn:** Integration tests versus unit tests, process spawning, ephemeral
ports, RAII, and the `Drop` implementation that stops test servers.

**Done when:** The existing four tests repeatedly pass in parallel without
`--test-threads=1`.

**Verification:** The four integration tests passed 50 consecutive runs with
Rust's default parallel test execution. The complete project test suite also
passed, and `cargo fmt --check` and `git diff --check` reported no issues.

**Quiz themes:** Port-allocation races, why `127.0.0.1:0` is useful, and what
cleanup through `Drop` protects against.

### 0.1.2 — Define the byte-range behavior contract

**Estimated focused time:** 45–75 minutes

**Status:** Complete (October 25, 2026)

Add tests for explicit, open-ended, suffix, oversized, reversed, malformed, and
unsatisfiable ranges; empty files; `HEAD` with ranges; and multiple ranges.
Continue to reject multiple ranges initially.

**Learn:** HTTP `200`, `206`, and `416`; inclusive endpoints; table-driven Rust
tests; boundary testing; and integer edge cases.

**Done when:** Tests fully describe the accepted range behavior. Production
changes in this task should only correct behavior exposed by those tests.

**Decision:** Support one explicit, open-ended, or suffix byte range. Clamp an
end beyond the file and let an oversized suffix select the full file. Reject
malformed, reversed, unsatisfiable, and multiple byte ranges with `416`. Range
unit names are case-insensitive; unknown units and every `Range` header on
`HEAD` are ignored, following RFC 9110.

**Verification:** Eight integration tests cover the complete range matrix,
empty files, and `HEAD` through real HTTP requests to the compiled daemon. The
complete project test suite, formatting check, Clippy with warnings denied, and
`git diff --check` pass.

**Quiz themes:** Range length calculation, suffix ranges, and when to return
`416 Range Not Satisfiable`.

### 0.1.3 — Record the HTTP-stack decision

**Estimated focused time:** 30–45 minutes

**Status:** Complete (October 25, 2026)

Write an architecture decision record comparing raw `std::net`, Hyper directly,
Axum with Tokio and Hyper, and Actix Web.

The starting recommendation is:

- Axum for routing and typed request handling;
- Tokio for the asynchronous runtime and file I/O;
- Hyper, through Axum, for HTTP parsing and connections;
- Tower and Tower HTTP for middleware; and
- Tracing for structured diagnostics.

Keep a small, tested range-selection abstraction while removing handwritten
HTTP parsing.

**Learn:** Framework versus runtime responsibilities, the Rust HTTP ecosystem,
and how an architecture decision record preserves context.

**Done when:** The decision, alternatives, consequences, and reversal path are
documented.

**Decision:** Use Axum for routing and typed request handling, Tokio for the
async runtime, Hyper through Axum for HTTP, Tower and Tower HTTP for middleware,
and Tracing for structured diagnostics. Keep range selection independent of
the HTTP framework. See
[ADR 0001](../adr/0001-use-axum-for-the-http-transport.md).

**Verification:** The ADR records the decision drivers, responsibility split,
concurrency model, four considered options, consequences, and a reversal path.
No production code or dependencies change in this task.

**Quiz themes:** What Axum, Tokio, Hyper, and Tower each do; why raw HTTP parsing
is risky; and the cost of adding an async ecosystem.

### 0.1.4 — Introduce the Axum application skeleton

**Estimated focused time:** 45–60 minutes

**Status:** Complete (October 25, 2026)

Add the async application structure alongside the existing server without
switching production startup yet. Create and test the player-page route through
Axum.

The likely source layout is:

```text
src/
  main.rs       CLI and process lifecycle
  server.rs     router and server setup
  range.rs      range-selection rules
```

**Learn:** Rust modules and visibility, `async fn`, Tokio's runtime, Axum
routers and handlers, and testing a router without opening a real socket.

**Done when:** The Axum player route passes an in-process test while the existing
executable remains functional.

**Decision:** Add `server::router()` as the seam for the new transport and keep
the raw TCP server as the executable's production path. The Axum router serves
the same embedded player page at `GET /`; its test calls the router as a Tower
service without binding a port. Axum, Tokio, and Tower are pinned to releases
compatible with the repository's current Rust 1.78 toolchain.

**Verification:** The in-process Axum route test returns `200`,
`text/html; charset=utf-8`, and the exact embedded player document. The existing
executable integration tests continue to pass, proving startup has not switched
yet. Formatting, Clippy with warnings denied, and `git diff --check` pass.

**Quiz themes:** Router construction, async functions, and the advantage of
in-process HTTP tests.

### 0.1.5 — Implement asynchronous media streaming

**Estimated focused time:** 60–90 minutes

**Status:** Complete (October 27, 2026)

Implement `GET` and `HEAD /media` in the new server. Open the configured file
asynchronously, seek to the selected offset, stream only the requested length,
preserve backpressure, avoid loading the movie into memory, and return the
correct headers.

Decide explicitly between Tower's filesystem service and a small streaming
adapter over Tokio file I/O. The current recommendation is a small adapter
because later milestones authorize stable media IDs rather than exposing
filesystem paths.

**Learn:** Axum application state, `tokio::fs::File`, asynchronous seeking,
streaming bodies, backpressure, and ownership across asynchronous handlers.

**Done when:** The new router passes the complete range test matrix.

**Decision:** Store the configured media path in Axum application state and use
a small streaming adapter built from `tokio::fs::File`, a length-bounded async
reader, and `tokio_util::io::ReaderStream`. This preserves backpressure and
prevents full-file buffering while keeping future media selection behind the
router rather than exposing filesystem paths. Move range selection into the
framework-independent `range` module so both transports use the same rules.

**Verification:** Seven in-process Axum tests cover the player, complete media,
supported ranges, rejected ranges, unsupported range units, empty files, and
range-ignoring `HEAD` requests. All eight executable integration tests continue
to pass against the raw TCP production path. Formatting, Clippy with warnings
denied, and `git diff --check` pass.

**Quiz themes:** Backpressure, why buffering an entire movie is undesirable,
and how one file segment becomes an HTTP response body.

### 0.1.6 — Switch the executable to the new server

**Estimated focused time:** 30–60 minutes

**Status:** Complete (October 27, 2026)

Make the daemon start the Axum/Tokio server. Remove the obsolete raw TCP parser,
manual routing, and thread-per-connection implementation while preserving the
CLI, loopback default, player page, full-file streaming, `HEAD`, and range
requests.

**Learn:** Async `main`, startup boundaries, dependency lockfile changes, and
why replaced code should be deleted rather than retained indefinitely.

**Done when:** The compiled binary passes all integration tests and a local
`curl` smoke test.

**Decision:** Make `main` asynchronous with Tokio, bind a
`tokio::net::TcpListener`, and pass the listener plus the configured Axum router
to `axum::serve`. Delete the handwritten request parser, response serializer,
blocking file streamer, accept loop, and thread-per-connection implementation.
Keep CLI parsing and process-level error reporting in `main`. Update executable
tests to compare HTTP semantics rather than header casing, order, or
serializer-added headers such as `Date`.

**Verification:** All seven in-process router tests and eight real-TCP
executable integration tests pass. A local daemon smoke test returned `200` and
the complete 38,392-byte file, then returned `206`, ten bytes, and
`Content-Range: bytes 0-9/38392` for `Range: bytes=0-9`. Formatting, Clippy with
warnings denied, and `git diff --check` pass.

**Quiz themes:** Thread-per-connection versus async I/O and what belongs in
`main` versus the application module.

### 0.1.7 — Define the HTTP error contract

**Estimated focused time:** 30–60 minutes

**Status:** Complete (October 27, 2026)

Define and test intentional responses:

- unknown route: `404`;
- known route with unsupported method: `405`;
- invalid or unsatisfiable range: `416`;
- malformed HTTP: HTTP-stack-controlled `400`; and
- media becoming unreadable after startup: a documented `404` or `500`.

Do not expose internal details in client responses.

**Learn:** Axum response conversion, typed errors, client-safe messages versus
operator diagnostics, and status codes as part of an API contract.

**Done when:** Every expected failure has a test and a documented status.

**Decision:** Use the following client-facing contract:

| Condition | Status | Owner | Client body |
| --- | --- | --- | --- |
| Unknown route | `404 Not Found` | Axum router | Empty |
| Known route with unsupported method | `405 Method Not Allowed` | Axum method router | Empty |
| Invalid or unsatisfiable byte range | `416 Range Not Satisfiable` | Application range handling | Empty; include `Content-Range` |
| Malformed HTTP syntax | `400 Bad Request` | Hyper | Stack-controlled and path-free |
| Configured media becomes unavailable after startup | `500 Internal Server Error` | Application media handler | Empty |

Treat disappearing media as `500` because the configured resource was valid at
startup and its later loss is an unexpected server failure, not an unknown HTTP
route. Do not include filesystem paths or internal error messages in application
responses. Keep malformed-request handling below the application router.

**Verification:** Nine in-process router tests cover successful behavior plus
`404`, `405`, and the existing `416` matrix. Ten real-TCP executable tests cover
the media contract plus stack-controlled malformed HTTP and media disappearing
after startup. The failure responses expose no configured filesystem path.
Formatting, Clippy with warnings denied, and `git diff --check` pass.

**Quiz themes:** `404` versus `405`, client versus operator error details, and
why malformed HTTP should be handled below the application router.

### 0.1.8 — Establish a resource budget

**Estimated focused time:** 30–45 minutes

**Status:** Complete (October 28, 2026)

Decide and document the maximum header size, header-read timeout, maximum active
connections or streams, shutdown grace period, overload behavior, and which
values will later become configurable.

**Learn:** Slowloris attacks, connection limits versus request limits, why a
total-response timeout is dangerous for video, and peak bandwidth versus
average bitrate.

**Done when:** Every limit has a reason and documented overload behavior.

**Decision:** Adopt explicit budgets for request heads, header-read time,
connections, active media bodies, request bodies, transport inactivity, and
shutdown draining. Limit the node to 64 accepted connections and 16 active media
bodies. Preserve unlimited healthy stream duration while closing connections
after 30 seconds without transport progress. Return `503` immediately when the
media-stream budget is exhausted rather than queueing. See the
[resource budget](../resource-budget.md) for values, lifetimes, overload
behavior, configurability, and implementation constraints.

**Verification:** Every resource has a concrete V0.1 value, rationale, ownership
lifetime, and overload behavior. The budget distinguishes connection capacity
from streaming capacity, stream duration from transport inactivity, and stream
count from bandwidth. It also records which limits can later become deployment
configuration and why a normal Tower concurrency limit is insufficient for a
streaming response body.

**Quiz themes:** Slow clients, stream duration versus idle duration, and why
limits should be justified rather than arbitrary.

### 0.1.9 — Implement timeouts and resource limits

**Estimated focused time:** 60–90 minutes

**Status:** Complete (October 28, 2026)

Apply the resource budget. Bound concurrency, time out incomplete headers,
prevent unbounded request bodies, preserve legitimate long-running streams, and
return an understandable overload response where possible.

Verify what each middleware timeout actually measures. A conventional request
timeout may stop measuring once response headers are produced rather than when
the streaming body finishes.

**Learn:** Tower middleware, semaphores and permits, streaming lifetimes, and
cancellation safety.

**Done when:** Slow or excessive clients cannot consume resources indefinitely
while normal playback remains stable.

**Decision:** Configure Hyper's HTTP/1 connection builder directly and keep
Axum as the application router. Limit request heads to 16 KiB, header fields to
64, header reads to 10 seconds, accepted connections to 64, active media bodies
to 16, request bodies to zero bytes, and transport inactivity to 30 seconds.
Connection permits cover the entire Hyper connection; media permits are carried
inside the response stream. Excess media requests receive `503` immediately,
while connection excess is held in the operating-system listen queue.

**Verification:** Real-TCP tests cover oversized request heads and excessive
header counts. Short-deadline transport tests verify incomplete-header and idle
connection closure, connection-capacity backpressure, and that continuing I/O
activity resets the inactivity deadline. Router tests verify zero-byte request
bodies and that media capacity remains occupied until a response body is
dropped.

**Quiz themes:** Where a concurrency permit must live, what a timeout covers,
and graceful overload behavior.

### 0.1.10 — Add graceful shutdown

**Estimated focused time:** 30–60 minutes

Handle interruption and termination signals. Stop accepting new connections,
allow active requests a bounded grace period, then exit cleanly without leaving
test processes behind.

**Learn:** Tokio signals, cooperative cancellation, graceful versus forced
shutdown, and why streams need a shutdown deadline.

**Done when:** An automated or precisely reproducible check demonstrates clean
startup and shutdown.

**Quiz themes:** Draining, cancellation, and why waiting forever is not graceful

### 0.1.11 — Add structured observability

**Estimated focused time:** 30–60 minutes

Add structured diagnostics for startup, bind address, request method and route,
status, duration, range requests, capacity rejection, shutdown, and internal
errors. Do not log media contents, future credentials, or unnecessary private
paths.

**Learn:** Tracing spans and fields, log levels, operational versus client-facing
errors, and privacy-sensitive logging.

**Done when:** A failed request can be diagnosed without exposing sensitive
information.

**Quiz themes:** Events versus spans, appropriate log levels, and data that must
not appear in logs.

### 0.1.12 — Add concurrency and adversarial tests

**Estimated focused time:** 60–90 minutes
